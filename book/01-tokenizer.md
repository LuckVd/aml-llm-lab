# Lab 01 原理：BPE Tokenizer

> 读顺序建议：本页 → bpe.py 的 TODO → 卡住再回来查。

## 1. 为什么需要 tokenizer？

模型只认数字。要把 "the cat" 变成 `[271, 1640]` 这样的 id 序列。
三种粒度：

| 粒度 | 例子 | 问题 |
|---|---|---|
| 字符级 | `t`, `h`, `e` | 序列太长，模型难学长依赖 |
| 词级 | `the`, `cat` | 词表爆炸 + 必然遇到没见过的词（OOV） |
| **子词（BPE）** | `the`, `cat`, `play`, `ing` | 两者平衡，GPT 系列的选择 |

## 2. byte-level 的关键一招

BPE 的初始词表不是字符，而是 **256 个字节**。任何字符串都能 utf-8 编码成字节序列，所以**永远不会 OOV**——中文、emoji、乱码都能表示。代价是中文一个字往往要 1–3 个 token。

## 3. BPE 训练 = 学"合并规则"

核心思想：**最高频的相邻字节对，应该合并成一个新 token**。

在语料上循环：

```
重复 vocab_size - 256 次：
    1. 数一遍所有相邻字节对的出现频率
    2. 挑最高的那对（并列时取字典序大的，保证确定性）
    3. 把它作为一条"合并规则"记录下来，新 token 进词表
    4. 把语料里所有该对替换成合并后的新 token
```

例：语料里 `es` 出现 12000 次（newest, widest...），第一次合并就是 `(e, s) -> es`。之后 `est` 成了高频对，第二次合并 `(es, t) -> est`。`the`、` ther` 这些常见词渐渐整体成 token。

**这就是"训练"**——没有梯度、没有神经网络，纯粹是统计 + 贪心。20 分钟写完的算法和 GPT-4 的 tokenizer 是同一族。

## 4. 预切分：为什么要先把文本切成小块？

如果不切，`(e, 空格)` 或跨词的 `(i, n)`（如 `wi` + `n`）也可能被合并，产生奇怪的跨词 token。GPT-2 的做法：先用正则把文本切成"词级"片段（`'s`、` word`、`123`、标点、空白……），**合并只在片段内部发生**。

看正则的四个主力分支（`book` 用 `regex` 库以支持 `\p{L}`）：

```
 ?\p{L}+      → " word"（一个可选前导空格 + 连续字母）
 ?\p{N}+      → " 123"（数字）
 ?[^\s\p{L}\p{N}]+ → "!!!"（标点）
'(?:[sdmt]|ll|ve|re) → 's 't 'll 等英文缩写
```

注意 ` word` 带前导空格是**故意的**：空格是英语里最高频的字节，跟词绑定后，"一个词 = 一个 token" 才可能实现。

## 5. 编码（encode）时怎么用学到的规则？

训练产出两样东西：`vocab`（id→字节）和 `merges`（有序合并规则表）。
编码新文本时**不能重新训练**，而是**按训练时的合并顺序重放**：

```
把片段拆成单字节
反复：找出当前序列里"训练时最早被合并"的那个相邻对，合并之
直到没有可合并的对
最后查 vocab 得到 id
```

"训练时最早" = merge 表里的序号（rank）。rank 小的规则优先执行，保证新文本的切分方式与训练时的切分方式一致。

## 6. 解码与容错

decode 就是把每个 id 的字节串拼起来再 `decode("utf-8")`。
因为任意 id 序列的字节拼接都可能是**非法 utf-8**（比如 LLM 幻觉出半个汉字），要用 `errors="replace"` 兜底成 `U+FFFD`，而不是让程序崩溃。
